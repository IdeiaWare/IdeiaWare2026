--- A.1 XSS (escape de saida) ---
Estrategia: <c:out> HTML-escapa todo output de dado do usuario. Foi feito em ONDAS porque
cada varredura cobria so um conjunto de telas/campos. Estado final: ZERO sink cru nos 2 projetos.
[SEC-03]  🟠 1a onda: escape nos campos de texto puro das telas de maior exposicao (admin/outros
   veem conteudo de terceiros): validar-ideia (titulo/nome/descricao + data-attrs), gerenciar-
   usuarios (nome/usuario/email), lista-ideia (titulo/descricao). Extensao: minha-ideia e
   detalhes-ideia (nome/titulo/descricao).
[SEC-03b] 🟠 escape estendido a mais texto de exibicao: lista-storytelling/canvas/caixa (nome+
   titulo); Toolkit: texto dos post-its de empatia (8 telas), nome da persona (list-personas),
   campos do POV (list-point-of-view). CUIDADO: a 1a passada de sed escapou DEMAIS (pegou
   onclick/value JS) e foi revertida; reaplicado so no display.
[SEC-05]  🟠 LIC: sinks de DOM client-side (XSS armazenado). Dado lido via trigger.data() (que
   DECODIFICA entidades HTML) e jogado por innerHTML/.html() RE-PARSEIA -> executa, mesmo com o
   c:out no atributo. Fix: helper escapeHtml() + wrap dos valores dinamicos em 6 JSPs (modais de
   lista-caixa/lista-canvas/validar-ideia/minha-ideia/gerenciamento/colaboracao).
[SEC-06]  🟠 Toolkit: STORED XSS nos 8 onclick inline (editAttribute x6 nas telas de empatia,
   buildPersonaEditModal em list-personas, buildPOVInfoEditOnModal em list-point-of-view). O EL
   ia DENTRO de uma string-JS dentro do atributo onclick: um valor com aspas quebra a string e
   executa (escape HTML simples NAO resolve — o browser HTML-decodifica o atributo). Fix (sem
   tocar no custom.js): onclick virou ESTATICO referenciando this.dataset.*, e os valores foram
   p/ atributos data-* escapados com c:out. (Editado byte-safe via Python: JSPs sao Latin-1.)
[SEC-07]  🔴 LIC: o XSS era MUITO mais amplo que o SEC-05. O usuario testou e <img onerror>

--- B.8 DAOs / CAMADA DE PERSISTENCIA (2026-07-02, branch dao-classes-robustez) ---
Varredura completa das 4 pastas edu.unisc.lic.{classes,dao,util,domain} (34 arquivos,
~2825 linhas), mesmo metodo do "prompt magico" (ver C, secao de metodologia), adaptado
p/ robustez de DAO/dominio: (1) operacoes sem tratamento de excecao adequado, (2) queries
que podem retornar null sem verificacao, (3) campos obrigatorios sem validacao na camada
de persistencia.

[DAO-SESSAO] 🔴 10 DAOs (CanvaDAO, CanvaexportDAO, ColaboracaoIdeiaDAO,
   ElementosStorytellingDAO, ExportFileDAO, IdeiaDAO, IdeiaUsuarioDAO, LogColaboracaoDAO,
   StorytellingDAO, UsuarioDAO) guardavam Session/Transaction como CAMPOS DE INSTANCIA da
   classe DAO (`private Session sessao; private Transaction transacao;`). Se a mesma
   instancia de DAO for reaproveitada entre requisicoes (padrao comum nesse tipo de
   codigo), duas threads pisam na mesma Session do Hibernate ao mesmo tempo — race
   condition real, nao teorica. Fix: Session vira VARIAVEL LOCAL de cada metodo (o
   GenericDAO ja fazia certo — serviu de modelo). Bonus: consultas so-leitura pararam de
   abrir Transaction (`beginTransaction()`) sem necessidade; o bloco de rollback manual
   (`catch HibernateException` + `System.out.println` engolindo o erro) saiu junto — so
   sobrou um `finally { sessao.close(); }` limpo. Resultado: -301 linhas liquidas (394
   remocoes, 93 insercoes) so nesse refactor, quase toda boilerplate repetida por metodo
   (ver explicacao do "porque encolheu tanto" no resumo do chat desta sessao).
   Bonus de seguranca no mesmo lote: `AssinaturaCaixa.assinar()` mudou de "erro -> retorna
   null" (cookie de assinatura HMAC quebrado passaria SILENCIOSO) p/ "erro -> lanca
   IllegalStateException" (aborta em vez de degradar o controle de seguranca calado).
[CFGBANCO-REMOVIDO] 🔴 IMPORTANTE, NAO CONFUNDIR com senha/anonimizacao (ver nota abaixo).
   Existia um mecanismo de config alternativa do banco: HibernateUtil checava se um
   arquivo cfgbanco.txt existia em $CATALINA_BASE/conf/ (via classes/ManipulaTxt.java) e,
   se sim, USAVA os dados de conexao (host/porta/schema/usuario/senha) desse arquivo em
   vez do hibernate.cfg.xml, descriptografando cada linha com classes/CriptografaDados.java
   (AES SEM MODO ESPECIFICADO — cai no default AES/ECB/PKCS5Padding, modo fraco). Achado:
   esse arquivo cfgbanco.txt NUNCA EXISTIU em nenhum deploy real do projeto — nem no Docker
   (entrypoint.sh so patcha o hibernate.cfg.xml via sed) nem no deploy manual Ubuntu (H.4,
   tambem edita o XML direto). Confirmado por grep: "cfgbanco" so aparecia neste proprio
   RELATORIO (nota historica), em NENHUM script/config real. Ou seja, era codigo morto
   desde sempre na pratica — a fraqueza do AES/ECB nunca era exercitada, mas nao valia a
